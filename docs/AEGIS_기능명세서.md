## 1. 문서 목적과 범위

본 문서는 AEGIS 시스템이 제공하는 기능을 식별자(ID) 단위로 정의한다. 각 기능은 **입력 → 처리 → 출력**과 담당 계층, 우선순위를 명시하여 개발·검증의 기준으로 사용한다.

**우선순위**

| 등급 | 의미 |
|---|---|
| **P0** | 시스템 성립 필수. 미구현 시 시연 불가 |
| **P1** | 감지 정밀화 및 차별성 기능. 전량 구현 목표 |
| **P2** | 여유 시 구현. 일정 부족 시 조정 |

**담당 계층**

| 표기 | 위치 |
|---|---|
| EDGE | Jetson Orin Nano Super 8GB |
| SRV | 메인 서버 (현장 내 노트북) |
| MCU | ESP32-POE-ISO |
| CLD | Google Gemini API (서버가 호출) |
| WEB | React 관제 화면 |

## 2. 용어 정의

| 용어 | 정의 |
|---|---|
| **2단계 캐스케이드** | 1단계 감지 모델이 사람·지게차를 찾고, 2단계 분류 모델이 사람 크롭을 받아 위반 여부를 판정하는 구조 |
| **후보 (Candidate)** | 엣지가 규칙에 걸린다고 판단해 서버에 보고한 위반 가능성. 아직 확정 아님 |
| **이벤트 (Event)** | 서버가 지속 조건을 확인해 확정한 위반 사건. DB 기록 단위 |
| **트랙 ID (track_id)** | 추적 모델이 부여하는 번호. **카메라 내에서만 유효**하며 전역 고유 아님 |
| **확정 (Confirm)** | 동일 트랙에서 동일 위반이 지정 시간 이상 지속되어 이벤트로 승격 |
| **해소 (Resolve)** | 위반 상태가 사라진 채 지정 시간 유지되어 시정 완료로 판정 |
| **쿨다운 (Cooldown)** | 재경고 사이의 최소 대기 시간 |
| **소실 (Lost)** | 진행 중 이벤트의 대상 트랙이 관측되지 않는 유예 상태. 아직 종결이 아니다 |
| **재결합 (Re-association)** | 소실된 트랙과 새로 등장한 트랙을 시공간 조건으로 동일 대상이라 판단해 이벤트를 승계시키는 처리 |
| **판정 불가 (Undetermined)** | 재결합에 실패해 시정 여부를 확인할 수 없이 종결된 이벤트. 시정률 분모·분자에서 제외하고 별도 집계한다 |
| **호모그래피** | 화면 픽셀 좌표를 실제 지면 좌표(m)로 변환하는 3×3 행렬 |
| **접지점 (Foot point)** | 사람이 지면에 닿는 지점. 거리·구역 판정의 기준 |
| **높이 비율 (Height ratio)** | 화면상 실제 마스크 높이 ÷ 해당 거리에서 서 있을 때의 기대 높이. 쓰러짐 판정의 핵심 지표 |
| **회색지대 (Gray band)** | 위험 임계값 부근의 거리 구간. 뎁스 검증 트리거 범위 |
| **정상 풀 (Normal pool)** | 평상시 장면 임베딩 집합. 이상 탐지 기준선 |
| **방송 후 시정률** | 경고 발동 이벤트 중 지정 시간 내 해소된 비율 |

## 3. 감지 아키텍처 개요

### 3.1 2단계 캐스케이드 구조

```
프레임
 └─ [1단계] 객체 감지 모델(단일) : person, vehicle(지게차) 2클래스만 감지
      ├─ vehicle → 추적 · 거리 계산 → 근접 판정
      └─ person  → 추적 · 접지점 · 구역 판정 · 자세 판정
            └─ 크롭 → [2단계] 분류 모델 → helmet_on / helmet_off
```

**이 구조를 채택한 이유**

1. **위반 귀속의 명확성** — 단일 단계로 안전모를 직접 감지하면, 사람이 겹쳐 있을 때 어느 안전모가 어느 사람 것인지 결정할 수 없다. 사람을 크롭해 분류하면 **위반이 특정 트랙에 명확히 귀속**된다.
2. **라벨링 비용 절감** — 분류 학습은 크롭 이미지에 라벨만 부여하면 되므로, 안전모마다 bbox를 그리는 것보다 데이터 준비가 빠르다.
3. **화면 표현의 단순화** — 박스는 사람·지게차만 그리고, 위반한 사람의 박스를 적색으로 표시한다.

### 3.2 감지 대상 요약

| 위반 유형 | 판정 주체 | 학습 필요 |
|---|---|---|
| `no_helmet` (안전모 미착용) | 2단계 분류 모델 | 필요 (분류 학습) |
| `proximity` (지게차 근접) | 1단계 감지 + 호모그래피 + 뎁스 | 필요 (vehicle 클래스) |
| `zone_intrusion` (금지구역 침입) | 접지점 + 폴리곤 판정 | 불필요 |
| `fall` (쓰러짐) | 마스크 기하 + 정지 지속 + 뎁스 | 불필요 |

## 4. 기능 목록

### 4.1 감지 (FN-DET)

| ID | 기능 | 우선 | 계층 |
|---|---|---|---|
| FN-DET-01 | 영상 수신 및 하드웨어 디코딩 | P0 | EDGE |
| FN-DET-02 | 1단계 객체 감지 (person · vehicle 단일 모델) | P0 | EDGE |
| FN-DET-03 | 객체 추적 및 트랙 ID 부여 | P0 | EDGE |
| FN-DET-04 | 2단계 안전모 분류 (크롭 기반) | P0 | EDGE |
| FN-DET-05 | 분류 결과 캐싱 | P0 | EDGE |
| FN-DET-06 | 접지점 산출 및 실좌표 변환 | P0 | EDGE |
| FN-DET-07 | 금지구역 침입 판정 | P0 | EDGE |
| FN-DET-08 | 지게차 근접 판정 | P1 | EDGE |
| FN-DET-09 | 마스크 기반 최근접 거리 | P1 | EDGE |
| FN-DET-10 | 쓰러짐 판정 | P1 | EDGE |
| FN-DET-11 | 뎁스 온디맨드 검증 | P1 | EDGE |
| FN-DET-12 | 이벤트 후보 생성 및 전송 | P0 | EDGE |

**FN-DET-01 · 영상 수신 및 하드웨어 디코딩**
- 입력: IP 카메라 서브 스트림(RTSP, **640×360**, H.264, 15fps) 2채널
- 메인 스트림(1920×1080, H.264, 15fps)은 서버가 별도로 수신한다. **두 스트림의 화면비는 16:9로 동일해야 한다**(API명세서 §1.2)
- 처리: NVDEC 하드웨어 디코더 사용. **CPU 디코딩 금지**(2채널만으로 CPU 포화)
- 성능 요구: 카메라당 8fps 이상

**FN-DET-02 · 1단계 객체 감지**
- 모델: **YOLO26-s-seg 단일 모델을 2클래스로 파인튜닝** (`person`, `vehicle`), TensorRT **FP16**
- 클래스: 2종만. 안전모는 여기서 감지하지 않고 2단계 분류가 담당한다
- 출력: 클래스, 신뢰도, bbox, **인스턴스 마스크**
- **세그멘테이션 헤드를 채택한 이유**: 접지점 산출(FN-DET-06), 마스크 최근접 거리(FN-DET-09), 자세 판정(FN-DET-10)이 모두 마스크를 전제로 한다. 박스만으로는 P1 정밀화 기능 전체가 성립하지 않는다
- **마스크 후처리는 GPU에 유지한다**: 프로토타입 계수 행렬곱 → 시그모이드 → 업샘플 → bbox 크롭 과정을 CPU(NumPy)에서 수행하면 인스턴스 수에 비례해 수십 ms가 소요되어 추론 시간보다 큰 병목이 된다. CUDA 상에서 처리하고 호스트로는 결과 배열만 반환한다
- **마스크 선택적 디코드**: 모든 인스턴스의 마스크를 매 프레임 디코드하지 않는다. 마스크가 필요한 대상(위반 후보 관련 person·vehicle, 뎁스 트리거 대상)만 디코드하고 나머지는 bbox로 처리한다

**단일 다중클래스 모델을 채택한 이유** (클래스별 모델을 각각 돌리지 않는 이유)
1. **연산 효율**: 1회 추론으로 두 클래스를 모두 얻는다. 모델을 분리하면 추론 시간과 엔진 메모리가 두 배가 되며, 프레임당 소요가 약 16~20ms에서 27~34ms로 증가한다
2. **정확도**: 단일 클래스 모델은 학습 중 다른 클래스를 배경으로만 취급하므로 "사람은 지게차가 아니다"를 학습하지 못한다. 다중클래스 학습은 두 클래스가 서로 hard negative로 작용해 혼동을 줄인다
3. 추적·후처리 파이프라인이 하나로 단순해진다

※ 감지와 분류를 분리하는 2단계 캐스케이드는 **태스크 자체가 다르므로** 정당하며, 위 논리와 상충하지 않는다.

- **클래스 명명**: 학습 데이터는 지게차 위주로 구성하되 대차·소형 산업차량을 일부 포함하고, 클래스명은 포괄적으로 `vehicle`을 사용한다. 실제 성능은 지게차에 최적화되면서 향후 장비가 추가되어도 클래스 구조를 바꾸지 않아도 된다
- **정밀도 방침**: FP16을 기본으로 한다. INT8은 속도 이득(약 0.8ms)에 비해 정확도 손실이 크고(mAP 0.480 → 0.449), JetPack 6의 INT8 빌드 이슈를 회피할 수 있어 **성능 미달이 실측될 경우에만** 검토한다
- **배포 검증 필수 사항**: YOLO26의 TensorRT 변환 시 신뢰도·박스 좌표가 어긋나는 사례가 보고되어 있다. 개발 1주차에 변환·정합성 검증을 선행하고, 문제 발생 시 YOLO11 계열로 대체할 수 있도록 백업 경로를 유지한다. TensorRT 엔진은 빌드한 GPU에 맞춰 튜닝되므로 **반드시 Jetson에서 직접 빌드**한다

**FN-DET-03 · 추적**
- 모델: ByteTrack (CPU)
- **person과 vehicle 모두에 track_id를 부여한다.** 지게차 추적이 필요한 이유:
  - 뎁스 검증 결과 캐싱의 키로 사용 (동일 사람-지게차 쌍 식별)
  - 이동 여부(`moving`) 판정 — 이동 중인 지게차는 위험도가 높다
  - 다수 지게차 구분

**FN-DET-04 · 2단계 안전모 분류**
- 모델: YOLO26-cls (분류 전용, 입력 224×224)
- 입력: 1단계에서 감지된 `person` bbox를 크롭한 이미지
- 처리:
  1. bbox를 약간 확장(패딩)하여 크롭 — 머리 부분이 잘리지 않도록
  2. **게이팅 검사** — 크롭 높이가 `cls_min_crop_px` 미만이거나 분류 신뢰도가 `cls_min_conf` 미만이면 **판정을 채택하지 않는다**
  3. 여러 사람이 있으면 **크롭을 배치로 묶어 1회 추론** (개별 호출 대비 GPU 효율 우수)
- 출력: `helmet_on` / `helmet_off` + 신뢰도 (**분류 모델의 클래스는 2종뿐이며 `unknown` 클래스는 두지 않는다**)

**게이팅 처리 방침 (`unknown` 클래스를 두지 않는 이유)**

모델에 제3의 클래스를 두면 학습 데이터에 "판정 불가" 라벨을 정의해야 하는데, 그 경계가 주관적이어서 라벨 품질이 떨어진다. 대신 **모델은 항상 2클래스로 답하게 하고, 그 답을 채택할지 여부를 엣지가 규칙으로 결정**한다.

| 상황 | 처리 |
|---|---|
| 게이트 통과 | 판정값으로 `helmet` 필드 갱신, `helmet_checked_at` 갱신 |
| 게이트 미통과 · 직전 캐시 있음 | **직전 값을 유지**하고 `helmet_checked_at`은 갱신하지 않는다(값이 오래됐음이 드러남) |
| 게이트 미통과 · 직전 캐시 없음 | 해당 트랙에 `helmet` 필드를 **싣지 않는다**. 서버는 `no_helmet` 후보를 생성하지 않는다 |

**카메라 설치 지침**: 서브 스트림이 640×360이므로 `cls_min_crop_px`(기본 64px) 게이트를 통과하려면 사람이 **프레임 높이의 약 18% 이상**을 차지해야 한다. 그보다 멀리 있는 작업자는 안전모 판정이 계속 보류된다.

해상도를 올리면 연산 예산을 초과하고 임계값을 낮추면 분류 정확도가 떨어지므로, **카메라를 대상에 가깝게·낮게 설치하는 것을 1순위 대응으로 삼는다.** 시연은 미니어처 모형으로 진행하므로 카메라 배치가 자유롭다. 작업자 모형이 프레임의 20~30%를 차지하도록 배치한다. 실제 값은 M7 임계값 튜닝 단계에서 실측으로 확정한다.

**타이머 규칙**: 게이트 미통과 구간에서 확정 타이머와 해소 타이머는 **초기화하지 않고 동결**한다. 작업자가 잠시 멀어졌다는 이유로 3초 확정 조건이나 10초 해소 조건이 리셋되면 판정이 성립하지 않기 때문이다.

- 비고: 원거리·저해상도 크롭을 억지로 판정하면 오탐이 발생한다. 판정 자체를 막는 대신 **판정의 채택을 막는** 방식이며, 스키마에는 2값만 존재한다

**FN-DET-05 · 분류 결과 캐싱**
- 목적: 안전모 착용 상태는 초 단위로 변하지 않으므로 매 프레임 분류는 낭비다
- 처리: `track_id`별로 분류 결과와 판정 시각을 보관하고, **캐시 유효기간**(기본 1초) 내에는 재추론 없이 캐시 값을 사용
- 효과: 8fps 기준 분류 호출량을 약 1/8로 감소
- 무효화 조건: 트랙 소실, 크롭 크기가 임계 이하로 변화, 유효기간 경과

**FN-DET-06 · 접지점 산출 및 실좌표 변환**
- 입력: 사람 마스크(없으면 bbox), 카메라별 호모그래피 행렬
- 처리:
  1. 마스크 픽셀 중 하위 8% 구간(발 영역) 추출 → x 중앙값을 접지점으로 결정
  2. 마스크 미사용 시 bbox 하단 중앙 사용
  3. 호모그래피 적용 → 지면 좌표(m) 변환
  4. 발 영역 가림·픽셀 부족 시 신뢰도(`foot_conf`) 하향
- 출력: 접지점 픽셀 좌표, 지면 좌표, 신뢰도

**FN-DET-07 · 금지구역 침입 판정**
- 입력: 접지점 지면 좌표, 등록된 구역 폴리곤(지면 좌표계)
- 처리: 점-다각형 내부 판정. 경계 버퍼 마진 적용, 진입/이탈 임계를 달리해(히스테리시스) 경계선 떨림 방지
- 출력: 침입 여부, `zone_id`

**FN-DET-08 · 지게차 근접 판정**

제조현장의 주된 위험 요인을 겨냥한 기능이다. 지게차는 제조업 사망사고의 기인물 1위이며, 적재 화물이 운전자 시야를 가려 보행자를 인지하지 못하는 구조적 취약성이 주요 원인이다.

- 입력: 사람 접지점, 지게차 위치·이동 여부, 클래스별 위험 반경
- 처리:
  1. 사람↔지게차 실거리 산출
  2. 위험 임계값 이내이면 근접 후보
  3. 회색지대이거나 화면상 겹침이면 뎁스 검증(FN-DET-11) 실행
  4. 지게차가 **이동 중**이면 위험도를 상향 조정한다(정지 상태보다 사고 위험이 높음)
- **위험 반경 기본값**: 지게차 3.0m (제조현장 실내 통행 기준). 근접 경고 임계값은 2.0m를 기본으로 하되 현장 통로 폭에 따라 조정한다
- 비고: 지게차는 **지면을 주행하는 장비**여서 바닥 접점이 명확하므로 호모그래피 기반 거리 계산이 정확하게 성립한다. 다만 포크가 전방으로 뻗은 상태는 bbox 기준으로 오차가 생기므로 마스크 기반 최근접 거리(FN-DET-09)로 보완한다

**FN-DET-09 · 마스크 기반 최근접 거리**
- 처리: 사람 마스크 윤곽과 지게차 마스크 윤곽의 점들을 각각 지면 좌표로 변환한 뒤 최소 거리 산출
- 목적: bbox 중심 간 거리는 다리를 벌린 자세나 **포크가 전방으로 뻗은 지게차**에서 오차가 크다. 실제 접촉 위험은 포크 끝단에서 발생하므로 윤곽 기반 최단 거리가 안전 판정에 정확하다
- 단계: 초기 구현은 bbox 기준, 이후 마스크 기준으로 정밀화

**FN-DET-10 · 쓰러짐 판정**

학습 없이 기하 정보와 시간 조건으로 판정한다. 아래 **세 조건을 모두 충족**해야 후보로 승격한다.

| 조건 | 산출 | 설명 |
|---|---|---|
| ① 낮은 높이 비율 | 마스크 높이 ÷ 해당 거리에서의 기대 높이 | 거리로 정규화하므로 원근에 무관하게 일관된 기준. 임계 이하이면 서 있지 않은 상태 |
| ② 수평 주축 | 마스크 PCA 주축과 수직축의 각도 | 서 있으면 수직에 가깝고 누우면 수평에 가깝다. ①과 독립적인 신호 |
| ③ 정지 지속 | 마스크 중심 이동량 + 형태 변화량이 임계 이하로 N초 지속 | **쭈그려 작업하는 사람은 상체·팔이 계속 움직이지만 쓰러진 사람은 움직이지 않는다.** 오탐 억제의 핵심 |

**뎁스 보강 (FN-DET-11 연계)**: 세 조건 충족 시 뎁스를 1회 실행해 마스크 영역의 **깊이 분산**을 확인한다. 서 있는 사람은 카메라로부터 거의 같은 거리에 있어 분산이 작고, 지면에 누운 사람은 깊이가 지면을 따라 퍼져 분산이 크다. 이를 통해 자세 판정의 신뢰도를 높인다.

**호모그래피 사용 방식 주의**: 호모그래피는 **접지점의 거리를 구하는 용도로만** 사용하고, 사람 마스크 전체를 지면으로 투영해 크기를 재는 방식은 사용하지 않는다. 지면 평면 가정에 의해 서 있는 사람의 상반신이 지면 위 먼 지점으로 투영되어 실제와 반대 결과가 나오기 때문이다.

**경고 처리 방침**: 쓰러짐은 대상자가 스스로 시정할 수 없는 상황이므로 **"착용하세요" 형태의 시정 유도 방송은 부적절**하다. 경광등 점등과 **관제 화면 긴급 알림 + 관리자 확인 요청**으로 처리하며, 별도의 구조 안내 음원을 사용한다. 시정률 지표에서도 별도 집계한다.

**FN-DET-11 · 뎁스 온디맨드 검증**
- 모델: Depth Anything V2 Small
- 트리거 (하나라도 충족 시 1프레임 실행):
  - A: 산출 거리가 회색지대 구간에 포함
  - B: 두 객체의 화면상 영역이 겹침(IoU > 0)
  - C: 접지점 신뢰도가 임계 미만
  - D: 쓰러짐 3조건 충족 (자세 검증용)
- 캐싱: 동일 객체 쌍(사람 track_id + 지게차 track_id)에 대해 0.5초 결과 재사용. 어느 한쪽이 지면 좌표로 임계 이상 이동하면 즉시 무효화
- 출력: 근접 확정 여부 / 자세 검증 결과(깊이 분산)
- 원칙: **거리 수치는 호모그래피 값을 사용하고, 뎁스는 앞뒤 분리 판별과 깊이 분산 확인에만 사용**한다. 단안 뎁스는 상대 깊이라 절대 거리가 부정확하다

**FN-DET-12 · 이벤트 후보 생성**
- 처리: 위반 유형별 규칙 충족 시 후보 객체 구성. **확정·경고 판단은 하지 않음**
- 출력: 이벤트 후보 JSON을 서버로 전송

※ 감지 대상 확장이 필요한 경우 데이터를 추가해 **재학습**한다. 오픈보캐블러리(제로샷) 방식은 채택하지 않는다(부록 A 참조).

### 4.2 이벤트 처리 (FN-EVT)

| ID | 기능 | 우선 | 계층 |
|---|---|---|---|
| FN-EVT-01 | 후보 수신 및 중복 병합 | P0 | SRV |
| FN-EVT-02 | 이벤트 확정 판정 | P0 | SRV |
| FN-EVT-03 | 해소(시정) 판정 | P0 | SRV |
| FN-EVT-04 | 쿨다운 및 재경고 | P0 | SRV |
| FN-EVT-05 | 이벤트 수동 정정 | P1 | SRV/WEB |
| FN-EVT-06 | 반복 위반 집계 | P1 | SRV |
| FN-EVT-07 | 트랙 소실 유예 및 재결합 | P0(유예) / P1(재결합) | SRV |

**이벤트 상태 전이**

| 상태 | 진입 조건 | 다음 상태 |
|---|---|---|
| `candidate` | 엣지 후보 최초 수신 | `active` / 소멸 |
| `active` | 동일 트랙·유형이 확정 지속시간 이상 유지 | `alerted` |
| `alerted` | 경고 발동 완료 | `resolved` / `re_alerted` / `lost` |
| `re_alerted` | 미해소 상태로 쿨다운 경과 → 재경고 | `resolved` / `re_alerted` / `lost` |
| `lost` | 대상 트랙이 관측되지 않음 (유예 상태) | 직전 상태로 복귀 / `expired` |
| `resolved` | 위반 소멸 상태가 해소 지속시간 이상 유지 | (종료 · **시정 성공**) |
| `expired` | `lost` 상태로 `track_lost_grace_s` 경과, 재결합 실패 | (종료 · **판정 불가**) |

```
candidate ─→ active ─→ alerted ⇄ re_alerted
                          │           │
                          └─────┬─────┘
                                ↓
                              lost ──재결합 성공──→ 직전 상태로 복귀
                                │                  (해소 타이머는 0부터 재시작)
                                └──유예 만료──→ expired (판정 불가)

            alerted / re_alerted ──위반 소멸 지속──→ resolved (시정 성공)
```

**`lost`를 둔 이유**: 트랙 소실을 즉시 종결로 처리하면 세 가지 왜곡이 발생한다.

| 실패 모드 | 트랙 소실을 즉시 종결할 경우 | 영향 |
|---|---|---|
| ① 시정하러 이동 중 트랙 이탈 | 실제 시정했으나 미집계 | 시정률 **과소** |
| ② 설비 가림으로 트랙 단절 | 동일 위반이 새 이벤트로 재생성 | 위반 건수 부풀림 + **중복 경고** |
| ③ 추적 ID 스위치(위반자 → 정상 작업자) | 위반이 사라진 것으로 관측 | **가짜 시정** → 시정률 **과대** |

③은 지표가 부풀려지는 방향이므로 가장 위험하다. 핵심 차별화 지표의 신뢰성이 직접 걸린 문제다.

**FN-EVT-01 · 중복 병합**
동일 `cam_id + track_id + 위반 유형`에 진행 중인 이벤트가 있으면 새로 만들지 않고 갱신한다. 트랙 ID가 끊겨 새 번호가 부여된 경우 FN-EVT-07의 재결합 절차를 우선 시도하며, 재결합에 성공하면 새 이벤트를 생성하지 않는다.

**FN-EVT-02 · 확정 판정**
후보가 확정 지속시간(기본 3초) 이상 연속 관측되면 이벤트로 확정한다. 확정 시점에 트리거되는 작업은 **실행 시점이 서로 다르다.**

| 작업 | 실행 시점 | 이유 |
|---|---|---|
| 경고 발동 (방송·경광등) | **즉시** | 1초 이내 요구사항 |
| DB 이벤트 기록 | 즉시 | |
| 고화질 키프레임 추출 | 즉시 | 확정 시점 프레임은 이미 링버퍼에 존재 |
| 클라우드 심층 분석 요청 | 즉시(비동기) | 키프레임만 있으면 되므로 클립을 기다리지 않는다 |
| **이벤트 클립 추출** | **`confirmed_at + clip_post_roll_s + 여유` 시점에 예약 실행** | 확정 순간에는 **사후 구간이 아직 녹화되지 않았다** |

클립 추출을 확정과 동시에 실행하면 사전 구간만 담기고 사후 구간이 비어버린다. 따라서 확정 시에는 추출 잡을 **큐에 예약**만 하고, 후행 세그먼트가 디스크에 기록된 뒤 실행한다. 이벤트 레코드는 `clip_status`(`pending` → `ready` / `failed`)로 상태를 노출하며, 대시보드는 `pending` 동안 키프레임을 대신 표시한다.

**FN-EVT-03 · 해소 판정**
경고 후 동일 트랙을 계속 관측하여, 위반 조건이 사라진 상태가 해소 지속시간(기본 10초) 이상 유지되면 `resolved`로 전이한다. `alerted_at`과 `resolved_at`의 차이가 시정 소요 시간으로 기록되며 **방송 후 시정률의 원천 데이터**가 된다.

**재결합 직후 해소 판정 (중요)**: 재결합으로 복귀한 이벤트는 위반이 이미 사라진 상태로 관측되더라도 **즉시 `resolved`로 전이하지 않는다.** 해소 타이머를 0부터 다시 시작해 `resolve_duration_s`를 새로 채워야 한다. 추적 ID 스위치로 다른 작업자가 트랙을 물려받은 경우를 방어하기 위한 규칙이며, 이 조건을 통과하면 최소한 "해당 위치에 해소 지속시간 동안 위반 없는 상태가 유지되었다"는 사실은 보장된다.

유형별 해소 조건:
- `no_helmet`: 분류 결과가 `helmet_on`으로 전환된 상태 지속
- `zone_intrusion`: 접지점이 구역 밖(이탈 히스테리시스 적용)
- `proximity`: 거리가 임계값 초과
- `fall`: 자세가 `standing`으로 복귀. **관리자 수동 확인으로도 종결 가능**

**FN-EVT-04 · 쿨다운**
미해소 상태에서 쿨다운(기본 30초) 경과 시 재경고. 재경고 횟수를 기록해 상습 위반 판단에 활용한다.

**FN-EVT-05 · 수동 정정**
관리자가 오탐으로 판단한 이벤트를 `false_positive`로 표시하거나, 미탐지된 시정을 수동으로 해소 처리할 수 있다. 정정된 이벤트는 지표 집계에서 제외된다.

**FN-EVT-06 · 반복 위반 집계**
동일 트랙 또는 동일 구역에서 최근 7일간 발생한 유사 이벤트 수를 집계해 이벤트 상세와 LLM 분석 입력에 포함한다.

**FN-EVT-07 · 트랙 소실 유예 및 재결합**

**① 소실 감지 및 유예 (P0)**
엣지로부터 `track_lost` 메시지를 수신하거나 해당 `track_id`가 `frame` 메시지에서 연속 미관측되면 진행 중 이벤트를 `lost`로 전이한다. `lost` 상태에서는 이벤트가 유지되고 쿨다운 타이머도 계속 진행하되, **재경고는 발동하지 않는다**(대상이 관측되지 않는데 경고하는 것은 무의미하다). `track_lost_grace_s`(기본 15초) 경과 시 `expired`로 종결한다.

※ ByteTrack은 자체 트랙 버퍼를 가지므로 짧은 단절은 엣지 내부에서 복구된다. 서버까지 도달하는 소실은 그보다 긴 단절이다.

**② 재결합 (P1)**
새 `track_id`가 등장하면 같은 카메라의 `lost` 이벤트를 대상으로 매칭을 시도한다. 모든 조건을 충족해야 한다.

| 조건 | 내용 |
|---|---|
| 카메라 동일 | `cam_id` 일치 (track_id는 카메라 내에서만 유효) |
| 시간 창 | 소실 시각과의 차이 `Δt ≤ reassoc_window_s` (기본 10초) |
| **시간 비례 반경** | 지면 거리 `≤ min(reassoc_max_speed_ms × Δt, reassoc_radius_cap_m)` |

반경을 고정값이 아니라 **경과 시간 × 최대 보행속도(기본 1.5 m/s)**로 산출하는 것이 핵심이다. 고정 반경은 작게 잡으면 정상적인 재결합이 실패하고, 크게 잡으면 인접한 다른 작업자를 잘못 흡수한다. 시간 비례 방식은 "1초 만에 다시 나타났다면 1.5m 이내에 있어야 한다"는 물리적 제약을 그대로 반영한다. 상한(`reassoc_radius_cap_m`, 기본 5.0m)을 두어 무한 확장을 막는다.

후보가 복수이면 지면 거리가 최소인 하나만 1:1로 결합한다.

**③ 재결합 성공 시 처리**

| 재결합 시점의 위반 상태 | 처리 |
|---|---|
| 위반 지속 중 | 직전 상태(`alerted` / `re_alerted`)로 복귀, **쿨다운을 이어받아** 중복 경고를 방지 |
| 위반 소멸 상태 | 직전 상태로 복귀하되 **해소 타이머를 0부터 재시작** (FN-EVT-03 참조). 즉시 시정 처리하지 않는다 |

이벤트의 `track_id`를 새 값으로 갱신하고, 이전 값은 `prev_track_ids`에 누적한다. `reassoc_count`를 증가시킨다.

**원칙**: 재결합은 **이벤트를 살려두는 처리이지 시정을 인정하는 처리가 아니다.**

**④ 보조 시그니처 (P2)**
재결합 게이트에 크롭 영역의 색상 히스토그램 유사도를 추가하면 오결합을 더 줄일 수 있다. 크롭은 2단계 분류를 위해 이미 생성되므로 추가 비용이 사실상 없다. **단 안전모 착용 여부는 게이트 조건으로 사용하지 않는다** — 그것이 판정 대상이므로 순환 논리가 된다.

### 4.4 기록 · 영상 (FN-REC)

| ID | 기능 | 우선 | 계층 |
|---|---|---|---|
| FN-REC-01 | 라이브 재스트리밍 | P0 | SRV |
| FN-REC-02 | 7일 링버퍼 녹화 | P0 | SRV |
| FN-REC-03 | 이벤트 클립 · 키프레임 추출 | P0 | SRV |
| FN-REC-04 | 이벤트 DB 저장 | P0 | SRV |
| FN-REC-05 | 저장 용량 관리 | P1 | REC |

**녹화 컴포넌트(REC) 분리**

7일 원본 녹화는 **엣지(Jetson)에 장착한 NVMe SSD**에 저장한다. 서버 노트북에는 이벤트 클립과 키프레임만 영구 보관한다.

| 저장 위치 | 내용 | 용량 |
|---|---|---|
| 엣지 SSD (500GB) | 메인 스트림 7일 원본 | 약 378GB |
| 서버 노트북 | 이벤트 클립 · 키프레임 · DB | 이벤트 수에 비례, 수 GB 수준 |

```
1920×1080 · 15fps · H.264 · 2.5 Mbps × 카메라 2대 = 5 Mbps
= 0.63 MB/s → 54 GB/일 → 7일 378 GB   (500GB 대비 76%)
```

고정 카메라에 움직임이 제한적인 제조현장이므로 2.5 Mbps로 실용 화질을 확보한다. 잔여 용량은 OS·모델·엔진 파일과 여유분이다.

**이 구조를 택한 이유**

1. **영상 원본이 현장 장비를 벗어나지 않는다.** 서버로는 이벤트 클립만 전송되므로 노출 범위가 최소화된다
2. 서버 노트북의 디스크 압박이 사라진다
3. 녹화는 디코딩 없는 리먹스 작업이므로 GPU 추론 예산에 영향을 주지 않는다

**대가**: 엣지가 정지하면 감지와 녹화가 함께 멈춘다. 단일 장애점이 늘지만, 엣지 정지는 `heartbeat` 단절로 즉시 드러나며 그 시점에 시스템 핵심 기능은 이미 정지 상태다.

**카메라 메인 스트림은 두 곳으로 동시 송출된다.** 서버(라이브 재스트리밍)와 REC(녹화)이 각각 독립 구독한다. 2.5Mbps × 2대 × 2구독 = 10Mbps로 유선 LAN에서 여유가 있다.

**REC는 독립 컴포넌트이며 서버와 HTTP로만 통신한다.** 개발 단계(M1~M8)에서는 서버와 같은 기계에서 실행하지만 **파일 경로로 직접 접근하지 않고 반드시 HTTP API(API명세서 §4.7)를 경유한다.** 실물 젯슨으로 옮길 때 주소만 바꾸면 되도록 하기 위함이다.

---

카메라 메인 스트림(1080p)을 서버가 재스트리밍해 관제 화면에 표시하고, REC가 동시에 세그먼트 녹화한다. 이벤트 확정 시 해당 타임스탬프 기준 **사전 구간(`clip_pre_roll_s`, 기본 10초) + 사후 구간(`clip_post_roll_s`, 기본 10초)** 클립과 **고화질 키프레임 2~3장**을 링버퍼에서 추출해 영구 보관한다. 엣지·서버 NTP 동기화가 정확한 구간 추출의 전제다.

**추출 타이밍 (FN-EVT-02 연계)**

```
confirmed_at 시점       : 키프레임 즉시 추출 (링버퍼에 이미 존재)
                          클립 추출 잡을 예약 큐에 등록, clip_status = pending
confirmed_at + post_roll : 사후 세그먼트 기록 완료
        + margin(2초)     : 예약 잡 실행 → 클립 추출 → clip_status = ready
```

세그먼트 파일이 아직 닫히지 않은 상태에서 잘라내면 파일 끝이 손상될 수 있으므로 여유(margin)를 둔다. 서버 재시작 시 `pending` 상태 잡은 DB에서 복구해 재실행한다.

**FN-AI-01 · 임베딩**
확정 이벤트의 키프레임을 Gemini Embedding 2로 벡터화하여 pgvector `halfvec(3072)` 컬럼에 저장한다. 호출만 클라우드에서 이루어지고 벡터는 로컬에만 보관한다.

**FN-AI-02 · 자연어 장면 검색**
구조화 가능한 조건(기간·카메라·유형)은 SQL 필터로 먼저 좁히고, 자유 문장 부분만 임베딩 유사도로 순위화하는 하이브리드 방식. 태그로 답할 수 있는 질의는 SQL만으로 처리한다.

**FN-AI-04 · 정상 풀 축적 및 이상 탐지**
- **샘플링 주기: 5분** (카메라 2대 기준 일 576회). 이벤트 임베딩을 포함해도 무료 한도(일 약 1,500회) 내에서 운용된다
- 서버가 자체 보유한 1080p 스트림에서 프레임을 캡처하므로 **엣지 추론 예산과 무관**하며, 비동기 처리로 실시간 루프에도 영향이 없다
- 시간대별로 정상 풀을 분리 축적하고, 신규 샘플과의 k-최근접 평균 거리가 임계를 넘으면 이상으로 표시
- **경고 방송·경광등은 발동하지 않고 대시보드 '주의' 알림으로만** 표기(조명·날씨 오탐 가능성). 이상 발생 시 해당 프레임을 LLM에 전달해 "무엇이 평소와 다른지" 설명을 부착

**FN-AI-05 · LLM 심층 분석**
위반 유형, 구역, 주변 지게차와 거리, 지속시간, 반복 횟수, 자세, 이상 점수, 유사 사례, 규정 조항을 하나의 구조화 컨텍스트로 합성해 Gemini Flash에 전달한다. LangGraph가 단계별 흐름을 제어하며 **메인 서버에서 실행**된다.

**FN-AI-06 · 규정 매핑**
위반 유형 → 산업안전보건기준 규칙 조항의 **사전 구축 매핑 테이블**로 결정적으로 연결한다. LLM이 조항을 생성하지 않도록 하여 오인용을 방지한다.

**FN-AI-08 · 챗봇 라우팅**

| 질의 유형 | 처리 경로 | 예시 |

| 통계·집계 | SQL 조회 | "이번 주 위반 몇 건" |
| 장면 검색 | 임베딩 유사도 | "사다리 근처 작업 장면" |
| 현재 상황 | 현재 프레임 → 멀티모달 LLM | "지금 2번 카메라 상황은?" |

**오버레이 시간 정렬 (FN-UI-02)**

라이브 영상과 오버레이 좌표는 **서로 다른 경로로 도착한다.** 영상은 카메라 1080p 메인 스트림 → 서버 재스트리밍 → 브라우저 디코드를 거치고, 좌표는 카메라 640p 서브 스트림 → 엣지 추론 → 서버 → WebSocket을 거친다. 두 경로의 지연이 다르므로 **NTP 동기화만으로는 화면상 정합이 맞지 않는다.** 시각이 같아도 도착 시점이 다르기 때문이다.

| 문제 | 대응 |
|---|---|
| 오버레이가 영상보다 **앞서 감** (좌표 경로가 더 빠름) | 클라이언트가 오버레이를 지연 버퍼에 담아두고 재생 중인 영상 프레임 시각에 맞춰 그린다. **버퍼 크기는 재생 경로에 따라 다르다** |
| 오버레이가 영상보다 **뒤처짐** | 마지막 좌표를 유지하되, `overlay_stale_ms`(기본 1000ms) 초과 시 박스를 흐리게 표시해 신뢰할 수 없음을 알린다 |
| 프레임 간 박스 떨림 | 트랙별로 좌표를 선형 보간해 렌더링 |

**재생 경로별 버퍼 (M1 실측 반영)**

라이브 영상 지연은 재생 방식에 따라 한 자릿수 배 차이가 난다. 단일 버퍼 값으로는 맞출 수 없다.

| 경로 | 실측 지연 | 버퍼 정책 키 | 기본값 |
|---|---|---|---|
| WebRTC (WHEP) | 0.27 ~ 0.34초 | `overlay_buffer_webrtc_ms` | 400 |
| LL-HLS (폴백) | 약 2.5초 | `overlay_buffer_hls_ms` | 2800 |

클라이언트는 현재 재생 경로를 알고 있으므로 그에 맞는 값을 적용하고, **화면에 현재 재생 경로를 표시**해 어떤 버퍼가 적용 중인지 드러낸다. 지연의 대부분(0.27초)은 카메라→mediamtx 구간에서 발생하므로 WebRTC 경로에서는 재생기 자체 지연이 크지 않다.

**구현 전제**: 서버는 `overlay` 메시지에 원본 프레임 시각 `ts`를 반드시 실어 보내고, 라이브 플레이어는 현재 재생 중인 프레임의 표시 시각을 알 수 있어야 한다(HLS·WebRTC 모두 타임스탬프 노출 가능). 정합 오차 목표는 ±100ms이다.

**오버레이 표시 규칙 (FN-UI-02)**

박스는 **`person`과 `vehicle`(지게차)에만** 그린다. 안전모는 별도 박스를 그리지 않고 사람 박스의 색상과 라벨로 표현한다.

**FN-SYS-04/05 · 지표 산출 정의**

```
시정률(correction_rate)     = resolved / (resolved + unresolved)
판정 불가율(undetermined)   = expired / (resolved + unresolved + expired)
```

| 대상 | 처리 |
|---|---|
| `resolved` (`resolve_window_s` 내) | 분자·분모 포함 |
| `alerted` / `re_alerted` 미해소 | 분모 포함 (unresolved) |
| **`expired` (재결합 실패)** | **분자·분모 모두 제외**, `undetermined`로 별도 집계 |
| `is_false_positive = true` | 전량 제외 |
| `fall` | 전량 제외 (대상자가 스스로 시정할 수 없음), 별도 카운트 |

**`expired`를 제외하는 근거**: 추적이 끊긴 이벤트는 시정 여부를 관측하지 못한 것이지 시정하지 않은 것이 아니다. 미시정으로 계산하면 시스템 성능이 부당하게 낮게 나오고, 시정으로 계산하면 지표가 부풀려져 방어할 수 없다. 제외하되 그 비율을 **함께 공개**하는 것이 정확하며, 검증 가능한 지표가 된다.

**표기 규칙**: 대시보드와 보고서는 시정률과 판정 불가율을 항상 병기한다. 예 — `방송 후 시정률 87% (판정 불가 5%)`

**부가 활용**: 판정 불가율은 그 자체로 **설치 품질 지표**다. 카메라 화각이 부적절하거나 가림이 심한 현장일수록 값이 상승하므로 카메라 재배치 판단의 근거로 사용한다.

## 5. 연산 예산

목표: 카메라 2대 × 8fps = **초당 16프레임**, 프레임당 예산 62.5ms.

| 단계 | 소요(추정) | 비고 |
|---|---|---|
| 디코드(NVDEC) · 전처리 · 메모리 전송 | 3~6ms | CUDA 전처리 기준 |
| ↳ 모델 입력 형태 | — | **640×384 rect letterbox** (정사각 아님, 아래 참조) |
| 1단계 감지 (YOLO26-s-seg FP16, 2클래스 단일) | 20~35ms | 세그멘테이션 헤드 포함. 동급 seg 모델의 Orin Nano 8GB 실측 보고치는 26~45ms 구간 |
| 마스크 디코드 · 후처리 (GPU, 선택적) | 3~8ms | CPU 수행 시 20ms 이상으로 급증하므로 GPU 유지가 전제 |
| 2단계 분류 (배치 처리) | 3~6ms | 224 입력, 캐싱으로 호출 빈도 1/8 감소 |
| ByteTrack | 1~2ms | CPU |
| 호모그래피·규칙 | ~0ms | CPU |
| **프레임당 합계** | **약 30~57ms** | 예산(62.5ms) 대비 **50~90%** |
| 뎁스(간헐) | 30~50ms/회 | 초당 2회 가정 시 +8% |

**모델 입력 해상도는 정사각이 아니다**

프레임이 640×360(16:9)이므로 기본값인 정사각 레터박스(640×640)를 쓰면 위아래에 회색 패딩이 140px씩 붙고, **그 패딩 영역까지 전부 연산한다.**
stride 32에 맞춘 `640×384` 로 rect 추론하면 패딩이 12px씩으로 줄어든다.

```
640×640 정사각 레터박스 : 409,600 px  (기준)
640×384 rect letterbox : 245,760 px  → 약 40% 절감
```

예산이 빠듯한 구간이므로 이 절감분은 실질적이다. 단 **학습과 추론의 입력 형태를 일치시켜야 한다.** 학습을 정사각 레터박스로 하고 추론만 rect로 하면 미세한 도메인 시프트가 발생하므로, 학습 시에도 동일한 형태를 사용하거나 최소한 검증 세트로 확인한다.

**추정치에 대한 주의**: 공개 벤치마크에 표기되는 수 ms 단위 수치는 GPU에 이미 적재된 텐서에 대한 **순수 추론 시간**이며, 디코드·전처리·전송·후처리를 포함한 실측치는 통상 그 3~4배로 보고된다. 위 표는 실측 보고치 기준으로 작성했다.

**예산 초과 시 대응 순서** (1주차 실측 결과에 따라 적용)
1. 마스크 후처리 GPU 이관 및 선택적 디코드 — 가장 큰 이득이 기대되는 지점
2. 목표 fps를 8 → 6으로 하향 (안전 감지는 초 단위 사건이므로 판정 품질 영향이 작다)
3. 모델 규모 `s` → `n` 하향
4. INT8 전환 검토 (정확도 손실 감수)

**모델 구성별 비교** — 클래스별로 모델을 분리할 경우 감지 소요가 두 배가 되어 프레임당 27~34ms(예산의 약 50%)로 증가한다. 단일 2클래스 모델은 16~22ms(약 25~35%)로 절반 수준이며 정확도 이점도 있어 이를 채택한다.

메모리 확보를 위해 **헤드리스 부팅**(약 865MB 절감)과 **디스플레이 없는 추론**(약 200MB 절감)을 적용한다. 모델 엔진을 분리하지 않는 것도 메모리 측면에서 유리하다.

## 부록 A · 미채택 기능 기록

아래 기능은 검토 후 **채택하지 않기로 확정**되었다. 구현 대상이 아니며, 화면·API·데이터 모델 어디에도 포함하지 않는다.

### A-1. 위험요소 자연어 등록 (오픈보캐블러리 / 제로샷 감지)

관리자가 대시보드에서 `"사다리"` 같은 객체명을 텍스트로 입력하면 학습 없이 즉시 감지 대상에 추가되는 기능. YOLOE 계열의 오픈보캐블러리 모델로 구현하는 방식을 검토했다.

**미채택 사유**

1. 사전 검증에서 사람은 비교적 안정적으로 감지했으나 **지게차 감지 성능이 입력 이미지에 따라 편차가 커** 신뢰성을 확보하지 못했다. 안전 시스템에서 감지 신뢰도가 입력에 따라 흔들리는 것은 수용할 수 없다
2. 시연을 미니어처 모형으로 진행하므로 **전용 파인튜닝이 어차피 필요**하다. 학습을 수행하는 이상 클래스를 추가하는 한계비용은 데이터 수집뿐이며, 제로샷의 이점이 상쇄된다
3. "정확도가 보장되지 않는 제로샷"보다 "전용 학습으로 지게차를 감지한다"가 **검증 가능한 설명**이다

**대체 방안**: 1단계 감지는 파인튜닝된 `person` / `vehicle` 2클래스 단일 모델로 수행한다. 감지 대상 확장이 필요하면 데이터를 추가해 재학습한다.

**주의**: 초기 화면 디자인 시안(`docs/AEGIS_front_design.pdf`) 4페이지 설정 화면에 「위험요소 등록 · 자연어」 패널이 남아 있으나 **이는 폐기된 안이다.** 구현하지 않는다.

## 부록 B · 디자인 시안과 명세서의 불일치

`docs/AEGIS_front_design.pdf` 는 프로젝트가 **건설현장에서 제조현장으로 전환되기 전**에 작성되었다. 시안의 레이아웃·정보 구조·색상 체계는 유효하지만, **텍스트 라벨과 도메인 용어는 본 명세서를 따른다.**

| 시안 표기 | 실제 구현 |
|---|---|
| 굴착 구역 | 지게차 통행로 (`forklift_lane`) |
| 굴착기 | 지게차 (`vehicle`) |
| 중장비 근접 | 지게차 근접 (`proximity`) |
| 사다리 위 작업 / 자재 적치 통로 | 제조현장 상황으로 대체 (프레스 구역 접근, 적재물 근접 등) |
| 「위험요소 등록 · 자연어」 패널 (YOLOE) | **삭제** (부록 A-1) |
| 유사 사고사례 "굴착기 선회 협착" | 지게차 후진 부딪힘 등 제조업 사례 |
